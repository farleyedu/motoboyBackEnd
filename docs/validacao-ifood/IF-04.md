# Validação do lote IF-04

Data: 13/10/2026. Escopo autorizado: contratos internos, schema aditivo e testes locais. Referência: [plano](../plano-integracao-ifood-produto-homologacao.md).

## Resultado

Build aprovado. 74 testes aprovados, nenhum falhou ou foi ignorado: 14 casos de contratos iFood, 7 testes de schema PostgreSQL e 53 casos de regressão existentes. Evidência final: [if04-regression.trx](if04-regression.trx). A execução isolada dos 21 testes novos também passou: [if04-tests.trx](if04-tests.trx).

## Implementação

- `Integrations/Ifood/Contracts/IfoodOrderIdentity.cs`: identidade oficial exige estabelecimento, merchant, UUID externo e pedido local; número de exibição preserva zeros e é distinto da chave externa.
- `Integrations/Ifood/Contracts/IfoodOrderSnapshot.cs`: snapshot mínimo com revisão, modalidade, estado remoto bruto, valores oficiais opcionais e janela; distingue saldo externo de total e deixa dados desconhecidos para revisão. Não é parser de payload oficial nem ledger de recebimentos locais.
- `Integrations/Ifood/Contracts/IfoodOperationState.cs`: estados internos, incluindo resultado incerto e desconhecido; desconhecido não é persistido como sucesso por fallback.
- `Migrations/Delivery/20261013_01_ifood_integration_schema.sql`: seis tabelas passivas para conexão, vínculo de pedido, inbox, snapshot, comando e disputa, com unicidade, integridade composta de estabelecimento e índices de processamento/recuperação.
- `Migrations/Delivery/20261013_02_ifood_integration_verify.sql`: exige migração anterior, tabelas e FKs compostas críticas antes de registrar versão verificada.
- `Migrations/Delivery/rollback/20261013_01_ifood_integration_schema.down.sql`: rollback de infraestrutura vazia, com locks para impedir escrita entre checagem e exclusão; recusa descartar dados iFood. Preserva pedidos/campos legados.
- `Tests/Unit/IfoodOrderContractTests.cs` e `Tests/Integration/IfoodIntegrationSchemaDatabaseTests.cs`: invariantes e comportamento real das constraints.

Nenhum controller, serviço existente, DTO público, tela, arquivo de configuração ou credencial foi modificado. Não há consumidor de eventos, importador oficial ou comando HTTP ativo neste lote. Schema não habilita uma conexão nem cria autorização de loja.

## Ambiente e execução

- .NET instalado no ambiente e target do projeto `net8.0`.
- PostgreSQL 17.11 portátil obtido da [página oficial de binários EDB](https://www.enterprisedb.com/download-postgresql-binaries), inicializado exclusivamente para testes em `docs/validacao-ifood/runtime/`.
- Instância escutou somente em `127.0.0.1:55473`, banco descartável `zippy_ifood_test`, sem credenciais de ambientes existentes. Autenticação trust foi usada exclusivamente nessa instância local temporária.
- Cada teste de integração criou um schema aleatório próprio e removeu-o ao finalizar. Verificação final confirmou zero schemas `ifood_schema_%` restantes. Servidor temporário foi encerrado após a execução, sem instalação permanente ou serviço Windows. Runtime/download permanecem inativos em `docs/validacao-ifood/runtime/`, ignorados pelo Git: a tentativa de limpeza via Remove-Item foi rejeitada pela política do ambiente e não foi contornada.
- `TEST_DELIVERY_DATABASE` foi definido somente nos processos de teste, sem alterar configuração persistente do usuário/projeto.

Comandos relevantes:

```powershell
dotnet restore --source https://api.nuget.org/v3/index.json --verbosity quiet
dotnet build --no-restore -v quiet
# Definir TEST_DELIVERY_DATABASE apontando para PostgreSQL LOCAL de testes antes dos comandos abaixo.
dotnet test --no-restore --filter 'FullyQualifiedName~IfoodOrderContractTests|FullyQualifiedName~IfoodIntegrationSchemaDatabaseTests' --logger 'trx;LogFileName=if04-tests.trx' --results-directory docs/validacao-ifood --verbosity quiet
dotnet test --no-restore --filter 'FullyQualifiedName~IfoodOrderContractTests|FullyQualifiedName~IfoodIntegrationSchemaDatabaseTests|FullyQualifiedName~PedidoCoreTests|FullyQualifiedName~ManualOrderRulesTests|FullyQualifiedName~DeliveryCompletionTests|FullyQualifiedName~DeliveryMigrationContractTests|FullyQualifiedName~DeliveryCompletionDatabaseTests' --logger 'trx;LogFileName=if04-regression.trx' --results-directory docs/validacao-ifood --verbosity quiet
```

O primeiro build sem restore falhou por cache incompleto de uma dependência existente de WebPush. Restore padrão tentou uma origem corporativa inacessível. Restore explícito pelo NuGet público resolveu sem editar NuGet.Config/csproj. Build completo apresentou 35 avisos em arquivos existentes, sem erros e sem avisos nos arquivos novos.

O primeiro ensaio encontrou uma fixture em que a unicidade de pedido já vinculado mascarava a FK cross-tenant. Corrigida a fixture para usar pedido livre de outra loja; execução final prova a FK composta. Não flexibilizamos a constraint para fazer o teste passar.

## Cenários comprovados

- Número iFood com zeros, UUIDs obrigatórios e identificação indisponível sem número inventado.
- MERCHANT/DELIVERY distinto de IFOOD, TAKEOUT e modalidade desconhecida.
- Total R$65 com R$20 online e R$45 pendente resulta em R$45 a cobrar; zero e ausência não se confundem; moeda desconhecida exige revisão.
- Valores negativos, fração de centavo e overflow rejeitados pelo contrato; janela invertida/incompleta rejeitada.
- Aplicação repetida de schema/verificação, sem duplicar versões nem alterar pedidos existentes.
- Verificação rejeita dependência ausente e ausência de FK composta.
- Mesmo número visível em dois merchants permitido; rebind de merchant e vínculo de pedido de outra loja rejeitados.
- Oito gravações concorrentes do mesmo evento geram um registro; outro merchant tem namespace independente.
- Snapshot, operação, tentativa vinculada e disputa não cruzam a fronteira merchant/pedido/estabelecimento.
- Estado processing exige lease completo; saída de processing exige retirar lease; resultado incerto não vira sucesso.
- Rollback vazio repetível preserva legado; rollback com dados é bloqueado.
- Regressões selecionadas de criação, regras manuais, migrações e conclusão/pagamento passaram.

## Limites e próximo passo

- Não houve chamada autenticada à API iFood, migração em banco real ou execução da API apontada para ambientes existentes.
- Não foi executada a suíte inteira do backend; foram selecionados os testes relevantes ao lote e aos fluxos locais mais próximos.
- Tabelas e contratos não implementam autorização de requests, criptografia de segredos/código, inbox workers, retry, conciliação, ledger ou regras públicas de UI. São responsabilidades dos próximos lotes.
- O migrator existente pode aplicar os novos SQLs no boot se `DeliveryTracking:ApplyMigrationsOnStartup` estiver habilitado. Esta validação não iniciou a API nem alterou essa configuração.
- Critérios de formato/elegibilidade/efeito remoto de código continuam pendentes do portal/sandbox; o schema preserva dados desconhecidos e não fixa tais regras.
- Próximo lote previsto: IF-05, autenticação centralizada e segredos, após confirmar contratos oficiais e apresentar arquivos/riscos/validações. Parte local pode ser validada com HTTP simulado; integração oficial depende de IF-00/IF-01.
